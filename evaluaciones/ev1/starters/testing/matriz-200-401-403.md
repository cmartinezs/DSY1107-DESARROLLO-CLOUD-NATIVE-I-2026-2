# Matriz de evidencia · 200 / 401 / 403

Esta matriz define los escenarios mínimos que deben poder reproducirse para demostrar autenticación y autorización.

| Escenario | Request | Credenciales | Permiso requerido | Resultado esperado | Qué demuestra |
|---|---|---|---|---|---|
| Público | `GET /public/health` | ninguna | ninguno | `200` | el recurso es accesible sin autenticación |
| Protegido sin token | `GET /api/profile` | ninguna | autenticación | `401` | la API exige autenticación |
| Protegido con token inválido | `GET /api/profile` | Bearer inválido, corrupto, expirado o no aceptable | autenticación | `401` | el Resource Server rechaza credenciales que no puede validar |
| Protegido con token válido | `GET /api/profile` | Access Token válido | autenticación | `200` | el token fue aceptado por la API |
| Operación por scope sin permiso | `POST /api/write/example` | Access Token válido sin `recurso.write` | `SCOPE_recurso.write` | `403` | autenticación correcta pero autorización insuficiente |
| Operación por scope con permiso | `POST /api/write/example` | Access Token válido con `recurso.write` | `SCOPE_recurso.write` | `2xx` | autorización por scope correcta |
| Operación por rol sin permiso | `GET /api/admin/example` | Access Token válido sin rol `ADMIN` | `ROLE_ADMIN` | `403` | autorización por rol correcta |
| Operación por rol con permiso | `GET /api/admin/example` | Access Token válido con rol `ADMIN` | `ROLE_ADMIN` | `2xx` | autorización por rol correcta |

## Interpretación de estados

### 200 / 2xx

La solicitud fue aceptada y procesada. En un endpoint protegido implica que autenticación y autorización cumplieron las reglas aplicables.

### 401 Unauthorized

Aunque el nombre HTTP diga `Unauthorized`, este estado representa normalmente un problema de **autenticación**:

- falta Bearer Token;
- token inválido;
- firma no válida;
- token expirado;
- issuer incorrecto;
- audience incorrecta;
- token no interpretable como Access Token aceptable por la API.

### 403 Forbidden

El usuario está autenticado y el token fue aceptado, pero no posee la autoridad necesaria para ejecutar esa operación.

Ejemplo:

```text
Access Token válido
+
no contiene recurso.write
+
POST /api/write/example
=
403
```

## Regla de diagnóstico

No confundir:

```text
401 → ¿quién eres / puedo confiar en estas credenciales?
403 → sé quién eres, pero no tienes permiso suficiente
```

## Traslado al proyecto real

Los endpoints de ejemplo existen solo para estabilizar la integración. Después el equipo debe trasladar la misma matriz a operaciones de su dominio.

Ejemplo:

```text
GET /api/libros
→ usuario autenticado

POST /api/libros
→ requiere libros.write

DELETE /api/libros/{id}
→ requiere rol ADMIN
```

No es obligatorio usar esos nombres; sí debe conservarse la diferencia observable entre autenticación y autorización.

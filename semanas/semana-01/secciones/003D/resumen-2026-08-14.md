## ¿Qué revisamos hoy?

### 1. API REST y semántica HTTP

Revisamos REST como un conjunto de principios, reglas y convenciones para diseñar APIs HTTP comprensibles y consistentes. El foco estuvo en identificar **recursos**, construir **paths** y elegir el **método HTTP** según la intención de la operación.

Ejemplos de recursos usados en clase:

- `/compras`
- `/inventarios`
- `/productos`
- `/ventas`

También diferenciamos rutas de colección y de un recurso particular:

```text
GET /compras
GET /compras/{id}
```

Y revisamos el uso de parámetros de consulta para filtros y paginación, por ejemplo:

```text
GET /compras?fecha=14-12-2025&elements=10&page=5
```

### 2. Métodos HTTP y operaciones sobre recursos

Relacionamos las operaciones habituales con su semántica HTTP:

| Método | Uso general |
|---|---|
| `GET` | Obtener uno o más recursos |
| `POST` | Crear un nuevo recurso |
| `PUT` | Reemplazar completamente un recurso existente |
| `PATCH` | Actualizar solo los datos enviados |
| `DELETE` | Eliminar un recurso |

Para `POST`, `PUT` y `PATCH` revisamos el concepto de **body** y el uso habitual de JSON, por ejemplo:

```json
{
  "id": "AAA-09",
  "fecha": "14-12-2025"
}
```

### 3. API, API Gateway y API Management

Distinguimos tres conceptos que suelen confundirse:

- **API:** contrato mediante el cual un sistema expone capacidades o datos.
- **API Gateway:** punto de entrada que recibe solicitudes y las enruta hacia uno o más servicios.
- **API Management:** conjunto más amplio de prácticas y capacidades para gestionar el ciclo de vida de las APIs.

Dibujamos el escenario en que varios servicios poseen sus propias URLs y cómo un **API Gateway** permite entregar al frontend un punto de entrada común, ocultando parte de la topología interna.

Entre las responsabilidades que puede asumir un gateway revisamos:

- routing/enrutamiento;
- políticas de seguridad;
- validación o gestión de tokens, por ejemplo JWT;
- CORS;
- rate limiting;
- encapsulamiento de servicios internos.

> Un API Gateway **no vuelve segura una API automáticamente**. La seguridad depende de las políticas y controles que efectivamente se configuren.

### 4. Versionamiento

Revisamos **versionamiento semántico**:

```text
MAJOR.MINOR.PATCH
1.0.0
1.0.1
1.1.0
```

La idea principal es distinguir entre cambios disruptivos que pueden romper compatibilidad y cambios que mantienen compatibilidad hacia atrás.

También se aclaró que **SemVer no es lo mismo que versionar el contrato de una API**. Una API puede exponer versiones mediante la URL, por ejemplo:

```text
GET /compras
GET /v1/compras
GET /v2/compras
```

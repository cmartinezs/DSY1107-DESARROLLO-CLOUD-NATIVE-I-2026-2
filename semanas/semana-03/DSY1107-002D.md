# Vertical A · contenido de hoy

## Paso 1 · recuperación activa

Sin RegistrApp.

Usar preguntas cortas y un caso ficticio simple:

```text
usuario → cliente web → IdP
cliente web → gateway → products-api
```

Preguntas:

1. ¿Quién es el cliente?
2. ¿Quién autentica?
3. ¿Quién emite el access token?
4. ¿A quién se presenta el access token?
5. ¿Para qué sirve PKCE?
6. ¿ID token y access token sirven para lo mismo?

Si el grupo responde con evidencia suficiente, avanzar. No repetir una presentación completa.

## Paso 2 · JWT como objeto observable

Trabajar con un JWT sintético ajeno a RegistrApp.

Material:

→ [JWT y claims](./01-jwt-claims.md)

Secuencia docente:

1. mostrar `header.payload.signature`;
2. decodificar header y payload;
3. identificar `iss`, `sub`, `aud`, `exp` y `scope`;
4. preguntar qué sabemos realmente solo por haberlo decodificado;
5. introducir firma/verificación;
6. discutir audience, expiración y permisos.

> **Poder leer un JWT no significa poder confiar en él.**

## Paso 3 · ejemplo suelto de autorización

Usar `products-api` solamente para el ejemplo.

```text
GET /products
requiere products.read

POST /products
requiere products.write
```

Discutir:

- sin token;
- token inválido;
- token válido con scope incorrecto;
- token válido con scope correcto;
- token técnicamente válido pero regla de negocio inválida.

→ [Seguridad de API y gateway](./02-seguridad-api.md)

## Paso 4 · mini laboratorio independiente

→ [Laboratorio JWT forense](./03-laboratorio-jwt-forense.md)

La evidencia pertenece al aprendizaje del contenido, no al desafío transversal.

El estudiante debe poder explicar:

- qué claim falló;
- por qué se rechaza;
- quién debería detectar el problema;
- por qué 401 y 403 no representan el mismo escenario.

## Gate antes de RegistrApp

Para habilitar transferencia al proyecto formativo, el estudiante/grupo debe poder defender al menos:

- access token vs ID token;
- decodificación vs verificación;
- `iss`, `aud`, `exp`;
- scope requerido;
- 401 vs 403;
- gateway vs backend.

DSY1107 · Identity as a Service

Identidad y acceso

Primero cierra el flujo base completo con Guest manual, MSAL, token y API Gateway. Después extiéndelo con self-service B2B y vuelve a probar todo el circuito.

Inicio del curso Documentación canónica Mi progreso

Regla de orden

No mezclar provisioning avanzado con OAuth/API antes de tiempo

La guía tiene dos partes. La extensión self-service comienza solo después de cerrar las pruebas y el troubleshooting del flujo base.

Parte I · Flujo base

Etapas 0–7

flowchart TD
    A[0 · Cuenta + Azure for Students] --> B[1 · Tenant / permisos]
    B --> C[2 · SPA App Registration]
    C --> D[3 · API + scopes]
    D --> E[4 · Guest/B2B manual]
    E --> F[5 · MSAL + PKCE + access token]
    F --> G[6 · API Gateway]
    G --> H[7 · Pruebas + troubleshooting + evidencia base]

Al terminar esta parte, el alumno ya debe poder distinguir tenant, Guest, login, access token, issuer, audience, scope, 401 y 403.

Etapas 0–1

Cuenta, suscripción y tenant

Verifica Azure for Students, distingue suscripción Azure de directorio Entra y confirma tenant y permisos.

Abrir guía desde el inicio →

Etapas 2–3

SPA, API y scopes

Registra la SPA como public client y expone la API propia con scopes. No uses client secret en navegador.

Ir a App Registration →

Etapa 4

Guest/B2B manual

Incorpora explícitamente un compañero como Guest y completa la invitación. Este Guest se usa para cerrar el flujo base.

Abrir Guest/B2B →

Etapas 5–7

MSAL, token, Gateway y pruebas

Completa Authorization Code + PKCE, access token para la API propia, validación en Gateway y la primera matriz integral de troubleshooting/evidencia.

Continuar con MSAL →

Parte II · Extensión self-service B2B

Etapas 8–14

flowchart TD
    A[8 · Comprender self-service] --> B[9 · Habilitar workforce tenant]
    B --> C[10 · Identity Providers]
    C --> D[11 · Atributos]
    D --> E[12 · Crear user flow]
    E --> F[13 · Asociar SPA + primer auto-registro]
    F --> G[14 · Segunda pasada integral de pruebas + troubleshooting + evidencia]

La extensión cambia el mecanismo de provisioning del Guest. MSAL, access token y Gateway se reutilizan y se prueban otra vez al final.

Etapas 8–9

Comprender y habilitar self-service

Separa workforce B2B de CIAM y habilita Enable guest self-service sign up via user flows en el tenant correcto.

Etapa 11

Atributos del primer alta

User flow

Etapa 13

Primer auto-registro real

Asocia la SPA, usa una identidad inexistente y comprueba el estado antes/después: inexistente → sign-up → Guest → sign-in posterior.

Etapa 14

Segunda pasada integral

Vuelve a probar provisioning, MSAL, token, Gateway y backend; además confirma que el Guest manual anterior no sufrió regresión.

Abrir pruebas finales →

Modelo mental

Qué cambia y qué permanece

flowchart LR
    MAN[Guest manual] --> COMMON[MSAL + access token + Gateway]
    SSR[Guest por self-service] --> COMMON
    COMMON --> API[Backend protegido]

Self-service cambia el provisioning. No reemplaza la autenticación OAuth/OIDC ni la autorización de la API.

DSY1107 · Identity as a Service

Identidad y acceso

Primero cerramos el flujo base completo. Después extendemos únicamente el provisioning de terceros con self-service B2B y repetimos la batería integral de pruebas.

Inicio del curso Documentación canónica Mi progreso

Regla de recorrido

Dos partes, dos gates

La Parte I debe quedar verde antes de comenzar self-service. La Parte II no reemplaza el flujo anterior: cambia cómo se aprovisiona el tercero y termina con una segunda pasada de pruebas, troubleshooting y evidencia.

Parte I · Flujo base obligatorio

Cuenta → Guest manual → token → API → evidencia

flowchart TD
    A[0 · Cuenta Duoc + Azure for Students] --> B[1 · Tenant / directorio / permisos]
    B --> C[2 · App Registration SPA]
    C --> D[3 · API propia + scopes]
    D --> E[4 · Guest/B2B manual]
    E --> F[5 · MSAL + Authorization Code + PKCE]
    F --> G[Access token para API propia]
    G --> H[6 · API Gateway / backend]
    H --> I[7 · Pruebas + troubleshooting + evidencia]
    I --> GATE{Gate Parte I aprobado}

No avanzar a self-service si aún no puedes demostrar Member + Guest manual, access token correcto, validación en gateway/backend y casos positivos/negativos reproducibles.

Cambiar provisioning sin cambiar el resto del sistema

No regresión

Ambos mecanismos deben coexistir

flowchart LR
    M[Guest manual] --> AUTH[MSAL + token]
    S[Guest self-service] --> AUTH
    AUTH --> GW[API Gateway]
    GW --> API[Backend]
    API --> Q{¿Guest manual sigue funcionando?}
    Q -- Sí --> OK[Extensión válida]
    Q -- No --> BUG[Regresión]

Evidencia

Demostrar checkpoints, no cada click

No publicar passwords, OTP, access/refresh tokens completos, client secrets, cookies de sesión, claves privadas ni credenciales Azure/AWS. La Etapa 14 debe incluir al menos un caso negativo y la prueba de no regresión.
